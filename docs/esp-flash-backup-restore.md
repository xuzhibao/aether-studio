# ESP Flash 分块备份与恢复（beta.4）

本功能在 **Plugins → Flash 备份/恢复** 面板中，通过本机 esptool 读取和写入 ESP 芯片的整片 Flash。它面向“动手前留一份完整备份，出问题后按范围恢复”的场景，默认按 512 KiB 分块、逐块校验、有限重试。

> 安全边界：本功能不修改 eFuse，不擦除整片 Flash，不记录密钥或 eFuse 原始内容，也不把备份写进当前工程目录。无法只读确认设备未受保护时，恢复会被明确拒绝，而不是“尽力尝试”。

## 前置条件

1. 使用 **Electron 桌面版**；浏览器预览没有串口与 esptool 能力。
2. 已安装 esptool，并在 **Plugins → Flash 备份/恢复 → esptool 可执行文件** 中填写路径。可填写：
   - esptool 可执行文件（例如 esptool 5 的 `esptool.exe`）；
   - `esptool.py`（会优先使用 PlatformIO 自带的 Python 运行，其次使用 PATH 中的 Python）。
   留空时依次使用环境变量 `AETHER_ESPTOOL`、PATH 中的 `esptool.py`。命令拼写会在启动时从 `--help` 实测：esptool 4 用下划线命令（`read_flash`），esptool 5 用连字符命令（`read-flash`）；不支持的能力会在界面上明确说明。
3. 关闭其他串口监视器、烧录工具或虚拟机串口转发。应用内的 Serial Monitor 与上传任务也会与 Flash 操作互斥：开始前会先断开监视器，断开失败则不开始。

## 备份

1. 在 **1. 选择设备** 中刷新端口并选择目标端口。端口列表来自操作系统，厂商与 VID:PID 不能证明板型或固件。
2. 点击 **读取设备信息**。界面显示芯片、修订、Flash 容量、厂商/型号、MAC 与 esptool 版本。**在未取得 Flash 大小前不会开始任何读取。**
3. 在 **2. 分块参数** 中选择块大小（默认 512 KiB）、波特率（默认 230400）与每块重试次数（默认 2）。
   - USB-Serial/JTAG 长读在 460800/921600 下容易损坏；失败时应用会自动把重试波特率减半，最低 115200。
4. 点击 **选择保存位置**，保存到工程目录之外。**目标文件已存在时不会覆盖**，请另选文件名。缓存目录同样不能位于工程或应用目录内（可用 `AETHER_FLASH_CACHE` 指定，默认 `S:\aether-flash-cache`）。
5. 点击 **开始备份**。进度显示当前偏移、块序号与百分比；某块最终失败时会显示 **失败偏移**。读取失败会自动降速重试，并沿用成功的更低波特率处理后续分块。
6. 随时可以 **取消**。取消或失败时不会生成成功备份文件；已读取的临时分块保留在缓存目录，便于排查。缓存目录默认是 `S:\aether-flash-cache`（存在 S: 盘时），否则是系统临时目录下的 `aether-flash-cache`。
7. 成功判定：所有分块读取成功、拼接后长度等于 Flash 容量、整片 SHA-256 计算完成，才会在目标位置出现 `.bin`，并同时写入 `.meta.json`。如果 `.bin` 已写入但元数据登记失败，界面会明确报告“不能视为成功备份”并给出临时元数据位置；只有 `.bin`、没有 `.meta.json` 的文件不能用于恢复。

### 备份元数据（`.meta.json`）

元数据只包含设备匹配与完整性核验所需的非敏感信息：

- 芯片、修订、Flash 容量、Flash 厂商/型号、MAC、特性；
- 文件长度、整片 SHA-256、块大小、块数、esptool 版本；
- 对 bootloader 魔数（0xE9）与分区表魔数（0xAA50）的健全性标记。

不包含密钥、eFuse 原始内容、分区内容或凭证。元数据缺失或格式不符时，恢复会被拒绝。

## 恢复

恢复是两阶段操作，**准备阶段不写任何字节**。

### 第一阶段：只读比较并生成计划

1. 选择备份 `.bin` 文件。应用读取同名 `.meta.json` 并显示备份设备与摘要。
2. 点击 **只读比较并生成计划**。应用会：
   - 核实备份文件长度与 SHA-256，并要求它是 **整片镜像**：文件长度必须等于元数据记录的 Flash 容量、且为 4 KiB 的整数倍；
   - 重新读取当前设备，核对芯片、Flash 容量、厂商/型号与 MAC；**MAC 必须存在且相同**，缺失或不同都按“身份不足”处理；
   - 用 `esptool get_security_info` 只读检查安全启动与 Flash 加密；
   - 检查当前 esptool 是否支持 `write_flash`（兼容 esptool 4 的下划线命令与 esptool 5 的连字符命令），以及 `--flash_mode keep` / `--flash_freq keep`（即能否在不改写镜像头的情况下写入）；
   - 按 4 KiB 对齐比较整片内容，列出 **将写范围**（偏移与长度）与总字节数。
3. 任一项不满足，计划会标记 **已拒绝恢复** 并给出原因，范围为空。常见原因：
   - 备份不是整片镜像（长度与记录的 Flash 容量不一致）；
   - 备份长度或 SHA-256 不一致；
   - 设备与备份记录不匹配，或备份/设备缺少 MAC；
   - 无法确认安全启动/Flash 加密状态，或设备已启用其中之一；
   - esptool 不支持写入，或无法保证不改写镜像头。
4. 如果设备当前内容已经与备份一致，计划会显示“无需写入”。

### 第二阶段：显式确认后写入并读回

1. 在确认框中输入界面给出的确认文字（`恢复-XXXX`，后四位来自备份记录的 MAC）。
2. 点击 **写入并读回核对**。应用会：
   - 重新核实设备身份、MAC 与安全状态，且当前 esptool 仍须支持写入并保证不改写镜像头；
   - 重新读取备份文件并与计划中的长度/SHA-256 比对；文件在准备后被替换或修改时拒绝写入；
   - 只写入计划中列出的范围：
     - **不传** `--flash_mode` / `--flash_freq` / `--flash_size`，因此不会改写 bootloader 镜像头；
     - **不传** `--erase-all`，不做整片擦除；
     - 不调用任何 eFuse 写入命令；
     - 仅在 esptool 支持时才传 `--verify`；
   - 写入与读回都使用所选的“每块重试”次数并在失败时降速重试；
   - 每段写入后，再单独 `read_flash` 读回原始字节，与备份切片逐段比对 SHA-256。
3. 只有全部计划范围写入成功且全部读回一致，才显示 **计划范围已写入并读回核对**。
4. 取消或失败时，结果会明确列出 **已尝试写入的范围**（含是否读回核对）与 **未尝试写入的范围**，并显示失败偏移；不会宣称恢复完成。此时设备可能处于部分写入状态，请重新执行“只读比较并生成计划”后再决定下一步。

### 恢复范围与时间

恢复只对 **计划中列出的范围** 做写入和读回核对；未写入区域只代表“准备阶段比较时与备份一致”。准备后如果设备继续运行，固件可能改写 NVS、OTA 数据等区域，这些变化不会被自动发现。因此：

- 计划有效期为 10 分钟；超时需要重新准备。
- 构建、上传或串口监视器连接会使计划失效。
- 准备后若设备运行过或不确定是否运行过，请重新执行“只读比较并生成计划”。

### 关于 bootloader 头参数

实测中，给 `esptool write_flash` 传 `--flash_mode` 或 `--flash_freq` 会改写 bootloader 镜像头并重算尾部哈希（即使写入的是备份文件）。本功能的恢复路径从构造参数层就排除了这些选项，并把 esptool 的 `ESPTOOL_FF` / `ESPTOOL_FM` / `ESPTOOL_FS` 环境变量固定为 `keep`，避免用户环境改变默认值。回归用例会检查写入命令中不出现这些参数、fixture 不会触发头部改写，并验证恢复后的镜像与备份逐字节一致（对写入范围而言）。

## 与监视器、上传任务的互斥

- 主进程用一个端口租约统一协调：串口监视器、构建/上传任务、Flash 备份/恢复（包括“读取设备信息”）都在开始前同步取得租约，互斥覆盖整个启动窗口，而不只是进程已运行之后。
- Flash 操作运行期间，Serial Monitor 与构建/上传任务都不能占用端口；界面会提示原因。
- 开始 Flash 操作前会断开监视器并确认端口已释放；释放失败则取消操作。
- 构建、上传或监视器连接会使已生成的恢复计划失效，需要重新准备。
- 串口异常断开（拔线、端口错误）会释放租约，不会让 Flash 永久判定为“被监视器占用”。

## 常见问题

- **读设备失败**：确认端口未被占用、驱动正常、板子处于可下载模式（必要时手动按住 BOOT 再复位）。
- **读取频繁损坏**：降低波特率到 115200/230400，增大重试次数；不要盲目提高块大小。
- **恢复被拒绝**：按界面给出的具体原因处理。安全启动/Flash 加密设备不会被写入；设备不匹配时不会盲写。
- **找不到元数据**：恢复必须同时有 `.bin` 与 `.meta.json`；只拷走 `.bin` 会失去可核验性。

## 测试与验收

- 自动化用例：`npm run smoke:flash`。它用**真实的 esptool 命令行表面**驱动一个**文件型假设备**（`scripts/fixtures/fake-esptool.mjs`），覆盖：块重试与降速、坏块与短读、失败时不生成成功文件、取消、头参数保持（含 `ESPTOOL_*` 环境变量）、校验失败、写失败偏移与未尝试范围、受保护/无法确认安全的设备拒绝、设备/摘要/整片长度不匹配拒绝、准备后备份被替换拒绝、缺 MAC 拒绝、不支持写入时拒绝、esptool 5 连字符命令与无 `--verify`、恢复取消的已尝试/未尝试范围。
- fixture 会拒绝未知命令行选项（与 argparse 一致），因此“误传 `--flash_mode`/`--verify`”会让用例失败，而不是被静默接受。
- 该用例不打开串口、不接触真实开发板，因此**不能证明**某块真实芯片已被正确写入或已启动。实机验收仍需按实际硬件步骤单独执行，并在操作前确认备份与还原路径。
